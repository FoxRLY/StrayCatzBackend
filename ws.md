# Протокол сокета

Один сокет на вкладку. Через него идут беседы и присутствие — разделять их
смысла нет, а держать два соединения ради этого дорого и ломается по-разному.

```
wss://api.straycatz.example/v1/ws
```

## Подключение

Токен передаётся подпротоколом, а не в query: адреса сокетов попадают в логи
прокси целиком, и класть туда JWT не стоит.

```
Sec-WebSocket-Protocol: straycatz.v1, bearer.<JWT>
```

Сервер отвечает выбранным подпротоколом `straycatz.v1`. Плохой или истёкший
токен — закрытие с кодом `4401` до первого кадра.

## Конверт

Все кадры — JSON одной формы:

```jsonc
{
  "t": "message.new",        // тип
  "id": "01J8...",           // ULID кадра; у серверных кадров монотонный
  "ts": "2026-09-19T21:14:07Z",
  "d": { }                   // полезная нагрузка
}
```

Клиентские кадры, на которые ждут ответ, несут `rid` (request id); сервер
возвращает его в ответном кадре. Это нужно, чтобы отправка сообщения
подтверждалась адресно, а не «каким-то следующим кадром».

## От клиента

| `t` | `d` | Смысл |
|---|---|---|
| `hello` | `{ lastEventId?, chats?: uuid[] }` | Первый кадр. `lastEventId` — то, что клиент видел до разрыва. |
| `chat.open` | `{ chatId }` | Человек открыл беседу: сюда шлём живое. |
| `chat.close` | `{ chatId }` | Ушёл с экрана беседы. |
| `message.send` | `{ chatId, body?, mediaId?, clientToken }` | Отправка. `clientToken` — uuid, генерит клиент. |
| `message.read` | `{ chatId, seq }` | Дочитал до `seq`. |
| `typing` | `{ chatId }` | Печатает. Без «перестал печатать» — гасится таймером на приёмнике. |
| `presence.set` | `{ status?, doing?, trackId?, positionSec? }` | Статус и музыка. |
| `ping` | `{}` | Если клиент хочет проверить живость сам. |

## От сервера

| `t` | `d` | Смысл |
|---|---|---|
| `ready` | `{ me, chats: ChatSummary[], missedFrom? }` | Ответ на `hello`. `missedFrom` — с какого `seq` в каких беседах есть пропуски. |
| `message.new` | `Message` | Новое сообщение в беседе, где человек состоит. |
| `message.ack` | `{ rid, clientToken, id, seq, createdAt }` | Подтверждение своей отправки. Клиент заменяет оптимистичную реплику по `clientToken`. |
| `message.updated` | `Message` | Правка или удаление (`deletedAt`). |
| `chat.read` | `{ chatId, userId, seq }` | Кто-то дочитал — обновить галочки и счётчик. |
| `typing` | `{ chatId, userId }` | Печатает. Приёмник гасит индикатор через 4 секунды. |
| `presence.changed` | `{ handle, status, doing?, listening? }` | Друг сменил статус или включил трек. Именно отсюда живёт «слушают вместе». |
| `feed.bump` | `{ count }` | Появилось новое в ленте. Только счётчик: подгружает клиент сам и когда захочет. |
| `error` | `{ rid?, code, message }` | Ошибка кадра. Соединение при этом не рвём. |
| `pong` | `{}` | |

## Порядок и пропуски

`seq` монотонный внутри беседы и выдаётся сервером. Клиент считает, что
получил всё, если `seq` идут без дыр; на дыре он догружает историю через
`GET /chats/{id}/messages?before=`. Восстанавливать пропуски через сокет не
нужно — HTTP для этого проще и не держит соединение.

После разрыва: `hello` с `lastEventId`, сервер отвечает `ready` с `missedFrom`,
клиент добирает пропущенное HTTP-запросами. Сервер ничего не хранит про
«недоставленное» — состояние восстанавливается из базы.

## Живость

Сервер шлёт ws-ping каждые 30 секунд, три пропущенных pong — закрытие `4408`.
Клиент переподключается с джиттером: 1с, 2с, 5с, 10с, дальше каждые 30с.

## Ограничения

* Тело сообщения — до 4000 символов, кадр — до 64 КБ. Картинки идут через
  `POST /media` и передаются как `mediaId`: гонять байты по сокету не нужно.
* `message.send` — не чаще 10 в секунду на соединение; превышение даёт
  `error` с `code: "rate_limited"`, но соединение остаётся.
* Одно соединение на вкладку, до пяти на человека. Шестое закрывает самое
  старое с кодом `4409`.

## Коды закрытия

| Код | Когда |
|---|---|
| `4401` | Нет токена, он испорчен или истёк |
| `4403` | Нет доступа к беседе |
| `4408` | Нет ответа на ping |
| `4409` | Слишком много соединений |
| `4500` | Внутренняя ошибка, можно переподключаться |

## Про реализацию на Quarkus

Смотреть стоит в сторону `quarkus-websockets-next` — у него нормальный
роутинг по типам кадров и человеческая интеграция с CDI, в отличие от
старого JSR-356. Рассылка между узлами — через `LISTEN/NOTIFY` Postgres,
пока узлов немного; когда станет мало, меняется на Redis pub/sub, и
протокол от этого не меняется.

Присутствие в базу писать на каждый кадр не нужно: держать в памяти узла,
сбрасывать в `user_presence` раз в 15–30 секунд и при смене статуса.
