# straycatz-ws

Kotlin + Quarkus (`quarkus-websockets-next`) реализация протокола сокета из
`docs/протокол-сокета.md`, плюс сигналинг звонков (`call.*`) — это
расширение поверх присланного протокола, там про звонки ничего не было.

Монолит, без отдельного сервиса под сокет — фанаут между узлами идёт через
Postgres `LISTEN/NOTIFY`, как советует дока. Когда узлов станет много,
единственное, что меняется — `EventBus` (замена на Redis pub/sub), сам
протокол и остальной код не трогаются.

## Быстрый старт

```bash
docker compose up -d          # postgres на 5432
./gradlew quarkusDev
```

Flyway накатит `src/main/resources/db/migration/V1__init.sql` сам
(`quarkus.flyway.migrate-at-start=true`). Сокет слушает `/v1/ws`.

## Структура

```
proto/      конверт кадра + DTO'шки d-пейлоадов (клиент/сервер)
registry/   состояние соединения (userId, какие чаты открыты) — свой
            реестр по connection.id(), не userData()/TypedKey, см. ниже
bus/        EventBus — LISTEN/NOTIFY фанаут между нодами
auth/       разбор bearer.<JWT> из Sec-WebSocket-Protocol
service/    ChatService, MessageService, PresenceService, CallService —
            вся бизнес-логика и SQL
ChatSocket.kt   сам @WebSocket-эндпоинт, роутинг по `t`
```

## Как устроен фанаут между нодами

`NOTIFY` в постгре режет пейлоад на 8000 байт, а тело сообщения — до 4000
символов, что в юникоде спокойно превышает лимит. Поэтому по каналу
`straycatz_bus` гоняется не сам кадр, а:

- либо маленький **готовый кадр** (typing, chat.read, presence.changed,
  call.ringing/accepted/declined/ended — всё это заведомо маленькое);
- либо **указатель** (`{"pointer":{"kind":"message","id":...}}`) на строку
  в Postgres — для `message.new/updated` и `call.signal` (SDP/ICE могут
  быть увесистыми). Нода-получатель сама дочитывает строку и уже из неё
  строит кадр.

Пишущая нода тоже проходит через `NOTIFY`, не рассылает локально напрямую
— так что если она сама держит одну из целевых вкладок, всё равно приходит
одним и тем же путём, без раздвоения логики.

Адресация — либо "все участники чата" (`chatId`, с флагом `liveOnly` для
typing — тем, кто чат открыл через `chat.open`, а не всем подряд), либо
"явный список userId" (presence, точечный `call.signal`).

## Что упрощено / на что обратить внимание перед продом

- **Код закрытия сокета** (4401/4403/4408/4409 из протокола). Я не смог
  на 100% подтвердить по документации, каким именно вызовом
  `WebSocketConnection` в websockets-next закрыть соединение с конкретным
  кодом (только `closeAndAwait()` без параметров подтверждён точно).
  Сейчас `ChatSocket.closeWithCode()` просто логирует предполагавшийся код
  и закрывает соединение как есть — поправьте эту одну функцию, сверившись
  с javadoc установленной у вас версии `quarkus-websockets-next`.
- **Эхо сабпротокола.** `Sec-WebSocket-Protocol: straycatz.v1, bearer.<JWT>`
  разбирается вручную в `AuthService` (это стандартный путь — доки прямо
  показывают `connection.handshakeRequest().header("Sec-WebSocket-Protocol")`).
  А вот `quarkus.websockets-next.server.supported-subprotocols` — имя
  свойства, которым сервер обязан заявить `straycatz.v1` в ответе на апгрейд
  (RFC требует эхо выбранного сабпротокола) — стоит перепроверить под вашу
  версию.
- **`hello.lastEventId`** в протоколе — это id последнего кадра вообще, а
  не per-chat `seq`. Точную "дыру" по чатам из одного значения не
  восстановить; `ChatService.missedFrom()` сейчас консервативно считает
  дырой всё, что новее `last_read_seq` — с запасом, ценой лишнего (дешёвого)
  `GET /chats/{id}/messages?before=`. Если нужна точность — разумно
  передавать в `hello` per-chat `lastSeq`, а не голый список id.
- **presence "друзья".** В протоколе нет графа контактов, поэтому
  `presence.changed` рассылается всем, с кем есть общий чат — разумное
  первое приближение для мессенджера, но не то же самое, что "друзья".
- **EventBus.onNotify** сбрасывает обработку в `vertx.executeBlocking`,
  чтобы не держать event loop на время SQL-догрузки по указателю — рабочий
  вариант для первой версии, но для высокой нагрузки стоит переписать на
  полностью non-blocking цепочку (`Uni`-чейнинг вместо `.await().indefinitely()`).
- **Пропало между вкладками — не мультиустройство.** `onClose` шлёт
  `presence.set(offline)` безусловно; если у человека 2–5 соединений
  (протокол это разрешает), закрытие одного из них его оффлайнит, хотя он
  ещё сидит с другой вкладки. Нужно проверять через `OpenConnections`,
  остались ли другие соединения этого userId, прежде чем гасить presence.
- **JWT.** `application.properties` ждёт `publickey.pem` рядом с классами
  (`mp.jwt.verify.publickey.location`) — для дев-окружения сгенерируйте
  пару ключей и подписывайте токены с claim'ами `sub` (uuid юзера) и
  `handle`; в проде это должно приходить из вашего auth-сервиса.
- **Звонки — только сигналинг.** Сервер передаёт offer/answer/ICE между
  участниками и хранит состояние (`calls`, `call_participants`), но сам
  медиапоток не трогает — это P2P WebRTC либо, если понадобится TURN для
  сложных NAT, отдельная инфраструктура, не эта часть.
- **`POST /media`, `GET /chats/{id}/messages?before=`** и прочий HTTP —
  за скобками этого куска, протокол их только упоминает как соседние
  ручки. Дока просит картинки гонять именно так, а не по сокету, так что
  `mediaId` в `message.send` — это уже готовый идентификатор из отдельного
  REST-эндпоинта.
